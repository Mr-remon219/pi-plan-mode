# v0.4 成熟化实施与验收

依据用户批准 v1 与独立计划审查，基线 a0a5f65。保持自由探索、原生文本流、TUI 明确批准；无运行时依赖，不修改 Core。

## 顺序
1. 测试先行锁定严格标签、嵌套/围栏/换行和失效事件。
2. artifact/v2 与 state/v2 分离；活动分支引用验证、v1 追加式迁移。
3. 来源消息身份单独记录；仅安全匹配的上下文副本删除旧计划正文。
4. 真实生命周期验证批准后 pending、磁盘读回、派发与工具快照时序；失败受限。
5. fresh 命令与工具漂移冲突提示。
6. 磁盘恢复、故障注入、50 KiB 修订成本基准、类型检查与离线烟测；文档据证据修订。

## 安全降级（父会话已裁决）
Pi 0.85.1 新会话无 assistant 时 appendCustomEntry 不落盘，没有公开 flush。不得伪造 assistant 或调用私有 _persist。未验证 pending 完整磁盘引用链时不派发，状态显示仅内存。fresh 若无法满足前置条件就报告不可用，不创建虚假成功记录。完整 fresh/空会话首次落盘前恢复验收须标未满足。磁盘读回不是 fsync 保证。写失败锁存，不能因重新读取内存分支清除。

## 验收
解析器 LF/CRLF、围栏、嵌套、多块、大小限制；正常当前轮次唯一来源捕获；20 次状态转换复用 artifact；v1、跨分支、compaction、损坏引用恢复；pending 不自动重放；出站协议字段保留；真实生命周期与多进程磁盘测试；1/5/10 次 50 KiB 修订成本对比。测试和源码类型检查、CLI/RPC 烟测、diff check 均需实际输出。父会话独立审查并负责发布，本实现者不提交、不发布、不改用户设置。

# Pi Plan Mode 成熟化计划

## 1. 目标与范围

将 `/home/mrremon/project/pi-plan-mode` 从可用的 v0.3.0 扩展，提升为**可恢复、可验证、低重复上下文成本的成熟 Pi 扩展**。

保留：
- 普通 assistant 文本流输出完整计划。
- 自由探索，不默认关闭 shell、网页、MCP、研究工具和子代理。
- 宿主管理状态、分支恢复和人工明确批准。
- 不修改 Pi Core，不新增运行时依赖。

本轮不承诺：
- 与 Codex、Claude Code 性能等价。
- OS 级只读沙箱。
- 任意第三方扩展间无冲突。
- 崩溃场景下严格 exactly-once 执行。
- 自动化 RPC 批准接口。

当前分支计划版本为 0，`plan_read` 确认尚无正文；本计划为首次正式提交。

## 2. 已核实事实与审查修正

- v0.3.0 已移除巨大 `plan_submit(markdown)` 调用，通过 `turn_end` 捕获普通文本计划。
- 当前正文重复存在于 assistant 历史、完整状态快照和执行 handoff；“只保存一次”的文档表述不准确。
- CustomEntry 本身不进入模型上下文。磁盘重复与模型 token 重复是两个问题，分别处理。
- 审批流程目前先 `exit()`，再 `sendUserMessage()`，存在交接失败后状态已解除的窗口。
- 现有测试覆盖主要逻辑，但没有验证真实磁盘会话的跨进程恢复。
- `main` 与 `v0.3.0^{}` 指向同一提交；审查者将 annotated tag 对象误判为不同提交，该指控不成立。
- Pi 提供 `ExtensionCommandContext.newSession({setup, withSession})`；新会话回调必须使用新的 context，不能复用旧扩展实例。
- 普通 `pi.sendUserMessage()` 返回 void，不能据此宣称消息已持久化或实施成功。

## 3. 架构决策

### 3.1 正文与状态分离

新增版本化记录：
- `pi-plan-mode/artifact/v2`：不可变正文、artifact ID、SHA-256、UTF-8 字节数、来源消息标识。
- `pi-plan-mode/state/v2`：phase、revision、artifact 引用、工具基线、交接信息。
- `pi-plan-mode/handoff/v2`：批准版本、handoff ID、目标会话信息及交接结果。

相同正文在同一活动分支内复用 artifact；状态转换不再重复写正文。

恢复只沿活动分支解析引用。缺失正文、摘要不匹配、未知格式或损坏状态均保持规划限制，并显示可诊断错误，不回退到其他分支计划。

兼容读取 v1 快照；首次需要写入新状态时进行追加式迁移，不重写历史 JSONL。

### 3.2 严格捕获，保留普通流式展示

继续使用 Pi 原生 assistant 渲染，不增加第二套实时渲染器。

仅接受：
- 规划态下当前有效生成轮次。
- 正常 `stop` 结束。
- 不含工具调用的最终消息。
- 恰好一个独立行、闭合且非嵌套的计划块。
- 非空正文，不超过 64 KiB，无危险控制字符。

解析器显式处理 LF/CRLF、代码围栏、额外开闭标签和重复事件；不使用宽松正则将代码示例误认为计划。

错误、中止、残缺输出不进入 `ready`。已有批准候选正文不被失败输出覆盖。部分输出仍由 Pi transcript 保留，本轮不新增独立草稿存储系统。

### 3.3 上下文只保留必要计划正文

只在发送给模型的上下文副本中处理，不修改历史 transcript：

- 根据已捕获的消息身份替换旧计划块为简短版本引用。
- 保留同消息中的非计划内容。
- 保留最近候选计划正文；执行交接正文进入上下文后，替换其历史 assistant 副本。
- 不删除普通用户需求、工具结果或未识别的计划示例。
- 不破坏 tool call/result 配对、消息签名和 Provider 必需字段；无法安全转换时跳过并报告限制。

`plan_read` 仍返回当前完整正文和版本；显式读取产生的工具结果不承诺零重复。

### 3.4 可诊断、保守恢复的批准交接

状态扩展为：

`off → planning → ready → handoff_pending → off`

批准后先记录 `handoff_pending`，包含批准 revision、artifact hash、handoff ID 和目标方式，再派发执行消息。

- 派发前继续限制实施工具。
- 仅将本进程用户审批产生、与有效 pending 记录匹配的交接认作授权；普通文本伪造标记不能批准。
- 通过真实 Pi 生命周期测试确认消息接收、提示词构建及工具恢复的顺序。
- 在执行请求已被接受且实施工具尚未使用的可验证边界，记录交接结果并解除限制。
- 如果公开 API 无法提供这个顺序保证，不伪造成功：保持 pending，要求用户在原生审阅入口重新确认。

同步派发失败保持受限。重启发现 pending 或结果不确定时，展示“重试交接 / 取消交接”，不自动重发。交接成功不等于实施完成。

### 3.5 清上下文执行

增加原生命令入口 `/plan --execute-fresh`，仍必须展示当前计划并明确确认。

使用 `newSession` 创建关联旧会话的新会话：
- 旧会话不删除，计划和探索历史可追溯。
- `setup` 写入批准 artifact、工具限制基线和待交接记录。
- `withSession` 只使用新 context，发送一次完整批准计划。
- 新会话保留项目规则和正常宿主配置，但不复制旧探索对话。
- 切换取消、回调失败或新会话派发失败均不自动执行或重复创建会话。

自动弹出的审阅面板不缓存 command context；需要新会话执行时提示使用该用户命令。这样避免在普通事件 context 中调用仅命令可用的会话 API。

### 3.6 保留自由探索，准确描述权限边界

默认策略不改成白名单，不添加容易误导的“strict 安全模式”。

继续：
- 阻止直接修改工具。
- 提示词禁止通过 shell、MCP、子代理间接实施。
- 明确声明非 OS sandbox。
- 显示当前保留的探索能力和权限限制。

对工具集合漂移采取保守策略：
- 记录扩展最后应用的工具集合。
- 不盲目用旧快照覆盖当前变化。
- 检测到无法归因的工具变化时提示冲突，禁止静默扩大权限；批准恢复前重新展示差异。
- 不宣称能识别宿主没有暴露的权限变更。

宿主 permission overlay 属于后续上游工作，不作为本轮交付前提。

2. **改进解析与幂等**

3. **迁移 artifact/state 存储**
   - 实现 v2 引用及 v1 兼容恢复。

4. **减少上下文重复**
   - 在上下文副本中替换可识别的旧计划。
   - 验证约束、证据和协议字段未被误删。

5. **修复批准交接**

7. **完善验证与文档**
   - 补跨进程恢复、兼容性检查及成本测量。
   - 对实现进行独立对抗审查；主执行者逐项复核，不按意见票数判断。

8. **发布**
   - 所有验收通过后发布下一可用 minor 版本，目标 `0.4.0`。
   - 发布 GitHub/npm，验证注册表版本后显式安装。
   - 核实真实加载路径和扩展错误；不远程打断正在运行的目标会话。

## 6. 测试与验收

### 正确性
- 有效中文长计划完整保存，包含代码块、表格和尾部标记。
- 嵌套、多块、围栏内伪标签、缺标签、超限、控制字符均不误批准。
- error、aborted、工具轮次、旧轮次、重复事件均不产生错误新版本。
- 用户输入、分支切换、编辑和取消使旧审批失效。

### 存储与恢复
- 同正文连续 20 次状态转换，只新增一份对应 artifact 正文。
- 多进程 `planning/ready/pending → 退出 → resume` 行为正确。
- compaction、分支切换后仍解析正确 artifact。
- v1 升级保持正文和限制；损坏引用保持受限。
- pending 恢复不自动执行。

### 交接与新会话
- 一次明确批准只派发一次执行请求。
- 派发异常不会留下静默解除限制的状态。
- 新会话只接收批准计划一次，不复制探索历史。
- 取消新会话不执行；旧会话可恢复查看。
- RPC/headless 无人工批准通道，不自动执行。

### 性能与证据
- 用相同 50 KiB 计划、1/5/10 次修订比较 v0.3.0 与新版本。
- 分别记录会话字节数、模型可见计划正文份数、捕获和恢复耗时。
- 旧计划全文不再随修订次数线性累积到出站上下文。
- 不把磁盘重复减少等同于 token 等比例减少。
- 不进行无控制的跨模型速度比较，不宣称达到竞品同等性能。

### 交付门槛
- 测试、源码及测试类型检查、真实 CLI/RPC 烟测、差异检查全部通过。
- 核心捕获使用真实宿主事件验证，不仅手动调用 hook。
- 没有未解决的错误批准、跨分支错配或静默权限扩大缺陷。
- 发布报告列出实际修改文件、验证命令、结果和剩余限制。

## 7. 风险与停止条件

- **API 生命周期不足：**无法证明安全交接顺序时保持 pending，不改用私有接口或假定 void 派发成功。
- **Provider 消息兼容：**不能安全替换历史内容时保留原文，明确成本限制。
- **扩展冲突：**无法判定权限变化来源时提示冲突，不静默恢复旧集合。
- **网络中断：**普通文本流仍可能断开；改造提高可见性和可恢复性，不保证网络可靠。
- **权限边界：**严格文件系统只读仍需外部 sandbox，不牺牲默认自由探索伪装安全。
- **范围膨胀：**不加入自动审稿代理、复杂质量评分、跨前端授权系统或自建沙箱。

完成标准是：**计划可读、状态可恢复、批准可追踪、失败不静默、成本可测量**，而不是功能数量追平原生客户端。
